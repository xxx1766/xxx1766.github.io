平台质量工程 (QA-Infra) + AI 研发平台 / DX

这段时间，我横跨两个生态做同一件事——把脆弱、隐式、不可信的系统，变成可声明、可门禁、可交接的体系。 在全球 GPU 调度平台 ieops-v2，我把 E2E 测试重构成可复用的声明式契约、把结构性永红的 CI 修成可信门禁、并按审计严重度逐条加固分布式深水区的缺陷；在 AI 研发平台 polyforge，我补齐了让 agent 自主驱动研发生命周期的架构地基——单一事实源、执行可观测、权限边界与入职体系。两条线由一个共享的场景契约 .scenario.md 连接。

仓库关系：用”工厂”造”产品”

我触达的 4 个仓库分属两个生态，由一个共享的”场景仓” polyforge-coding 桥接。

生态一：polyforge —— AI 原生研发平台（”工厂”）

经典三层分工：服务端 / 客户端运行时 / 内容。

  • aihub（Go + PostgreSQL 服务端）：work item / 记忆 / MCP = 唯一事实源。用 scenario_ref 把 wi SHA-pin 到场景仓某次提交。
  • marketplace（Claude Code 插件市场）：托管 polyforge 插件（/pf-* skills、hooks、statusline）= agent 客户端运行时。
  • polyforge-coding（场景仓）：agent 执行的”程序”，同时是两个项目的 scenario 仓。我的 E2E + await_ci 契约就住在这里，被两个生态复用。

生态二：ieops —— 被开发的产品（”流水线上的产品”）

  • ieops-v2（K8s-native 全球 GPU 智能调度与推理平台）：CRD + controller-runtime，10 个独立服务进程。我在这里做 E2E 体系 / CI 绿化 / 后端健壮性与审计整改。

配套仓库：ieops-karmada、ieops-titan、ieops-utils、ieops-kube、ieops-clouds、ieops-doc、proxy-server

两条工作主线

同一套”声明式场景即契约”的思想，在两个平台上各自落地，最终交汇。

主线一 · 全球 GPU 调度平台的可信交付防线

ieops-v2 · 质量保障 + 分布式健壮性

为什么做： GPU 跨集群调度的致命 bug 潜伏在 K8s 声明式 API + 分布式时序里，code review 抓不到——必须有真实环境 E2E 才能暴露；但旧 E2E 硬编码、CI 结构性永红，门禁立不起来。

  • 测试从代码降维成声明式契约；映射反转 O(files×scenarios)→O(services)
  • 修结构性永红 CI：区分”解析期崩溃 vs 测试失败”
  • 按审计严重度逐条加固：agent panic-safety、部署阻断、Draining 状态合并正确性
  • 反向捞出 finalizer 竞争泄漏 / condition.reason 正则 / gpunode CRD 腐烂

主线二 · 让 AI agent 自主驱动研发生命周期

polyforge (aihub · marketplace · polyforge-coding)

为什么做： agent 要自主跑 wi 全生命周期，但当时架构有”双事实源”（服务端 graph vs scenario .md）必然漂移、执行黑盒不可观测、门禁错误耦合到可选的 branch-protection。

  • 单一事实源坍缩：DROP 服务端 step graph，scenario .md (SHA-pin) 成唯一 SoT
  • status-only 上报，让黑盒执行可观测
  • 门禁解耦到显式 check 白名单，不依赖可选配置
  • agent 自治有界：不抢 merge、不抢资源、不盲目 auto-fix

五类工作 · 按含金量排序

维度：技术深度 × 影响范围 × 是否建体系/可复用 × 是否触核心。🏁 标为收尾可交接。

🥇 ieops-v2 E2E 测试体系建设与契约工程化

把测试降维成声明式契约，三层正交解耦、跨仓复用，并反向捞出多个分布式潜伏 bug；最后做成 validator + CI 门 + 模板 + scaffold 的机器自强制、可交接体系（#54/#56）。

  • ✅ 建体系 / 可复用
  • ✅ 跨仓打通
  • 🏁 收尾可交接
  • ⚠️ E2E 执行本身仍未进 CI

🥈 ieops-v2 后端健壮性加固与审计整改

系统性按审计严重度整改（最后阶段 #13/#25/#29 逐条收口）：agent watch 循环 panic-safety、每个 Helm-default 部署启动即失败的部署阻断缺陷、Draining 状态合并正确性、finalizer 竞争泄漏、CRD 退役——触近核心、高影响。

  • ✅ 命中崩溃 / 部署阻断 / 状态正确性
  • ✅ 每项补回归测试
  • 🏁 收尾可交接

  • ✅ 解析期崩溃 vs 测试失败

重要 Bug 档案

挑出印象最深的几个——多数不在业务逻辑表面，而潜伏在分布式时序、K8s API 约束、CI 求值时序、渲染生命周期里。

🔴 CI 永久卡死 · secrets context not in if

类型： Critical · ieops-v2

发现： 自 PR #185 起每次触发都生成一个 conclusion=failure 且 jobs 为空的 run，无法 re-run，test/lint/test-e2e 三个必需检查永久红、PR 根本无法合并。根因：secrets context 在 if: 条件中不可用，workflow 在解析期就崩溃（而非运行期失败）。

处理： 把 secret 映射进 step 的 env:（那里可求值），判空逻辑挪进 run: shell；保留合法的 needs.* 在 if: 中。

14279fe · ieops#42 区

🔴 每个 Helm-default 部署启动即失败 · gpunode

类型： Critical · ieops-v2

发现： 审计 C1/H8——newGPUDataSource() 的 switch 从不处理 "gpunode"，但 DefaultGPUDataSource 与所有 Helm bff values 默认全是 gpunode，于是每个用 Helm 默认值的 BFF 一启动就走 error 分支挂掉。根因：GPUNode CRD 已在 IEBE-1546 删除、状态迁到 VNode，默认配置没跟上。

处理： 标准化到 vnode、退役 gpunode：改 business.go 默认值 + 3 份 values.yaml + flag help，并加”gpunode 现在显式报错”的回归测试。

659c8ab · ieops#13

🟠 故障恢复控制环静默瘫痪 · condition.reason 正则

类型： High · ieops-v2

发现： 由 E2E full-suite scenario 04 跑出来——MD 永远卡在 Deploying、RetryExhausted 状态机永不触发。根因：CRD 给 Condition.reason 的正则不允许 .，而 VK node 名永远含 .；旧代码拼 reason 时只把 - 换成 _、漏了 .，导致每次 status patch 都被 API server 拒。

处理： 抽 sanitizeNodeID，用 strings.NewReplacer 同时替换 - / .；加 TestProviderFailedReasonMatchesCRDRegex 正则回归。

8a54953 · IEBE-1607

🟠 孤儿资源泄漏 · finalizer 时序竞争

类型： High · ieops-v2

发现： ScaleDown 时 vk-node 的 Deployment + NodePort Service + K8s Node 三者泄漏成孤儿，DeleteDeployment("") 报 “resource name may not be empty”。根因：MD finalizer 先于 NodeAutoscaler 删了 sub-cluster Node 对象，extractProvisionedInfo 早退、拿不到编码在 Node 名里的 groupID，删除目标名留空。

处理： 利用命名约定里已有的冗余——直接从 nodeName 的 . 后缀解析出 groupID 做无状态恢复，让既有删除逻辑照常工作（不依赖任何外部存储）。

e2ca94e · IEBE-1617

🟠 agent watch 循环崩溃 · MustParse panic

类型： High · ieops-v2

发现： 审计 H1——畸形/恶意 NetworkVolume 的 spec.size 会让 resource.MustParse panic，直接打挂整个 agent watch 循环（createPV/createPVC）。

处理： 换成 parseVolumeSize（ParseQuantity）对畸形输入返错不崩；nil sub-cluster client 在四条路径全部加 guard；补错误路径 table test。

2f25362 · ieops#25

🟠 删除中途被翻回 Running · 状态合并

类型： High · ieops-v2

发现： 审计 H4/M1——updateMergedPhase 会把 Running/Deploying 盖到正在 teardown 的相位上，draining 中的 mdep 若有瞬时 Ready pod 就被翻回 Running，删除流程错乱。

处理： 加 isTeardownModelDeploymentPhase guard（Draining/Drained/Failed），只在 teardown 相位拦截、正常 Deploying→Running 仍前进；加 Draining-preserved 测试。

2f25362 · ieops#25

🟡 “全白 chain” 不是数据 bug · 渲染生命周期

类型： Medium · polyforge

发现： statusline 进度链全白冻结，第一反应是数据错——但一查 .chain.json 数据完全正确。根因：Claude Code 只在会话”有消息更新”时才重跑 statusLine；/pf-execute 在后台 subagent 里跑、主会话整段 idle → 零 re-render → 卡在 claim 时刻的快照。是渲染/生命周期问题，不是逻辑问题。

处理： 给 pf-init 接管写 statusLine.refreshInterval:3（让它在定时器上也重跑），并对旧安装 back-fill——不改任何逻辑。

5b7bf16 · marketplace

🟡 orphan chain.json · 终止事件时序

类型： Medium · polyforge

发现： wi 结束后 chain.json 偶发泄漏成孤儿、清不掉。根因：pf_complete_attempt 在 PostToolUse hook 跑之前就把 state file 删了，hook 的 findActiveState 因此找不到 wi。

处理： resolveWiId——终止事件改从 toolInput.work_item_id 直接取 wi，不再依赖已被删除的 state file。

c06a9aa · marketplace

🔵 越权克隆 · 可见 ≠ 授权

类型： Security · aihub

发现： polyforge init 会把 caller 根本没有任何 role 的 public-only 项目（如 tether）也自动克隆进工作区。根因：GET /v1/projects 同时返回 public+member+owned，旧 init 只检查 Visible 就克隆——把”在列表里可见”误当成”同意克隆”。

处理： 加 callerHasRole 谓词（owner 或 members 命中才克隆），并 thread 进 writeMemberPolyforgeYAML；空 uid 保留 legacy 行为，避免 whoami 失败时静默产空 yaml。

96af08f · aihub#129/#144

贯穿始终的三条原则

不是零散任务的堆叠，而是一个统一工程思想在两个领域的落地。

  1. 单一事实源：凡有第二个会腐烂的同步源（服务端粗 graph、fine→coarse 映射、branch-protection required set、glob→scenario 表、散落的 //nolint），一律砍掉或收成一处。
  2. 解耦语义不同的耦合：可见 ≠ 授权、绿 ≠ merge、wrap 信号 ≠ merge 强制。
  3. 优雅降级、无静默错误：畸形 CRD 不 panic 而返错、拒绝静默不可选的场景、CI 红 pause 给人带日志——绝不盲目 auto-fix、绝不静默吞错。

“我把调度平台的质量保障从不可维护、不可复用、不可信，重构成可声明、可复用、可门禁、可交接的体系——离开时，系统是干净的。”
